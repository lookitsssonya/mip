# ADR 0001: Использование AI Gateway

## Статус

Принято.

## Контекст

Сервис `ai-recommendations` генерирует рекомендации сопутствующих
товаров с помощью LLM. На старте рассматривались варианты:

1. **Прямой вызов LLM из `service`** — просто, но создаёт vendor lock,
   дублирует обработку ошибок, не позволяет централизованно управлять
   квотами и метриками.
2. **Вызов LLM из `controller`** — нарушение слоёв, невозможно
   тестировать.
3. **Введение отдельного слоя `AiGateway`** — единая точка входа
   для всех вызовов LLM.

## Решение

Ввести класс `AiGateway` в пакете `llm`, который:

- выбирает провайдера по конфигурации (`llm.active-provider`);
- маршрутизирует запрос к соответствующему `LlmClient`;
- обрабатывает ошибки;
- выполняет fallback на резервного провайдера;
- пишет метрики через Micrometer (`llm.requests{provider,status}`);
- логирует вызовы без чувствительных данных.

## Последствия

### Положительные

- **Отсутствие vendor lock** — смена провайдера не требует изменения
  бизнес-логики.
- **Централизованная обработка ошибок** — в одном месте.
- **Fallback** — при сбое основного провайдера используется резервный.
- **Observability** — все вызовы логируются и метрятся.
- **Тестируемость** — `AiGateway` легко подменяется моком в тестах.

### Отрицательные

- **Дополнительный слой** — чуть больше кода.
- **Сложнее отладка** — нужно смотреть логи `AiGateway`, а не только
  `LlmClient`.

### Нейтральные

- Требуется конфигурация `llm.active-provider`.
- Требуется регистрация всех `LlmClient` как Spring-бинов.

## Альтернативы

- **Spring Cloud Gateway** — избыточно для одного сервиса.
- **Resilience4j Circuit Breaker** — можно добавить позже поверх
  `AiGateway`.
- **Прямой вызов** — отклонено из-за vendor lock.
